# A Simple Example

This document walks through how to write and run a simple Hybrid Pluck program which
demonstrates a number of the capabilities of Hybrid Pluck.

A Hybrid Pluck program consists of a sequence of *top-level forms*, which may be:
- type definitions (using `define-type`),
- function definitions (using `define`), and
- queries (using `query`).

For example, the following program defines a function and queries the posterior of the
parameter `p`, given that the observed output was one.

```scheme
;; Define a function with parameter p.
(define (generate-number p)
    ;; flip a coin with probability p
    ;; if true, sample from a normal distribution with higher mean and variance
    ;; if false, sample from a normal distribution with lower mean and variance
    (let ((hi (flip p)))
        (if hi (normal 2.0 2.0) (normal 0.0 1.0))))

;; Example query:
;; Posterior distribution of probability p,
;; given that the number is equal to one.
(query 
  ;; Query name:
  posterior-given-equal-to-one
  ;; Query:
  (let ((p (beta 1.0 1.0)))
    ;; Compute the exact posterior P(p | x = 1)
    (Posterior 
      p 
      (real_eq (generate-number p) 1.0))))
```

More examples can be found in the `examples` directory, catalogued in
[Examples](examples.md).

In Visual Studio Code, we have found that when editing `.pluck` files, it is nice to set
the language to Clojure (to use Clojure syntax highlighting and auto-formatting via the
`cljfmt` extension).

## Running a Hybrid Pluck Program

Programs can be run either using `cargo run` or by building a binary using `cargo build`
and running it directly:
```
cargo run --release examples/simple_example.pluck
cargo build --release && ./target/release/pluck examples/simple_example.pluck
```

All definitions are loaded into the top-level environment, and the results of each query
in the file are printed to the console.
```bash
cargo run --release examples/simple_example.pluck
    Finished `release` profile [optimized] target(s) in 0.13s
     Running `target/release/pluck examples/simple_example.pluck`

posterior-given-equal-to-one:
  p  0.9999999999999999
    ├ 57.89%
    │       p ~ Beta(1.0000, 2.0000)
    └ 42.11%
            p ~ Beta(2.0000, 1.0000)
```

## Reading the output

**The first line is the query name**, from `(query posterior-given-equal-to-one ...)`.

**`p` is the value the query expression took**, and `0.9999999999999999` is its
probability. In this case `p` is a *symbolic value* which represents a Beta variable. 
Since this is the only query output, it has probability `0.9999999... ~= 1`.

**The tree is the distribution for `p`.** It appears whenever a displayed value is reachable along
several discrete execution paths whose continuous posteriors differ. Each branch shows its
share of that value's probability, and the conjugate posterior along it, while the overall
tree represents a mixture model.

In this program the branching comes from `hi`, the latent coin flip inside
`generate-number`. If `hi` is true, the observation `x = 1` was generated by
`(normal 2.0 2.0)`; if false, by `(normal 0.0 1.0)`. Each path gives a different
posterior update for `p`, so the answer is a two-component mixture:

* with weight 57.89%, `p ~ Beta(1,2)` — `hi` is false, and `x` is sampled from `(normal 0.0 1.0)`
* with weight 42.11%, `p ~ Beta(2,1)` — `hi` is true, and `x` is sampled from `(normal 2.0 2.0)`

False is somewhat more likely because the `hi` branch has a larger variance, hence a smaller density
at `1.0`.

A purely discrete query has no such tree. From `examples/burglary_alarm.pluck`:

```
burglary-given-called:
  False  0.9970065507586945
  True  0.002993449241305545
```

**Display.** Values are sorted by probability, descending. Only the top ten are
printed in full; past that, components with probability below `1e-6` are collapsed into a
single line reading `... and N more components (combined prob: ...)`.

Sampling queries — `PosteriorSamples` and `Gibbs` — instead print one value per line with
no probabilities. See [Queries](queries.md#reading-the-results) for details.

Not every query terminates: computing an exact distribution requires the queried
expression to be forceable in finitely many steps for every random seed. The precise
requirement differs per query form — see [Queries](queries.md#termination) — and
[Sharp Edges](sharp_edges.md#termination-and-non-termination) shows what it looks like
when a query does not terminate, and how to rewrite it so that it does.

## Environment variables

| Variable | Effect |
|---|---|
| `PLUCK_STATS` | Print BDD/SPN sizes and per-stage timings to stderr |
| `PLUCK_DISPLAY_PRECISION` | Decimal places for posterior parameters (default 4) and mixture weights (default 2) |
| `PLUCK_EQ_TOL` | Relative tolerance for the equality gate on sampled continuous assignments; raise it if a Gibbs chain stalls spuriously |

`PLUCK_STATS` is the one to reach for when something is slow:

```bash
PLUCK_STATS=1 cargo run --release examples/coinBias.pluck
```

```
=== PLUCK_STATS ===
worlds (value,guard pairs)            : 1
continuous latents (Beta/Gaussian/…) : 1
guard vars allocated (discrete bits)  : 5
factorizer recursive calls            : 467
guard nodes      : sum=5  max=5  mean=5
SPN nodes (TREE) : sum=1  max=1  mean=1
SPN nodes (DAG)  : per-world-max=1  all-worlds-unique=1  intern-table=7
SPN leaf nodes   : sum=1  (max sum-node-count=0, max product-node-count=0)
posterior mixture components (total)  : 1
time (s): parse=0.0001  symbolic-exec=0.0002  wmc=0.0000  posterior=0.0000  flatten=0.0000  display/naming=0.0000  total=0.0004
```

The sizes are deterministic; the timings on the last line vary from run to run.

* **`guard vars allocated`** — how many random discrete choices the program made.
* **`guard nodes`** — the size of the BDD. If this is far larger than the variable count,
  it may be due to a bad variable order; see
  [Sharp Edges](sharp_edges.md#2-variable-order).
* **`posterior mixture components`** — The number of mixture components in the continuous posterior. 
This is exponentially large for many hybrid models.

The `time (s):` gives timing for different stages:
* **`parse`** — reading and parsing the program.
* **`symbolic-exec`** — symbolic execution of the program. Since Hybrid Pluck is *lazy*, this *includes* BDD 
construction, which is done on the fly as the programs symbolically executes.
* **`wmc`** — Weighted model counting, which constructs the likelihood SPN from the BDD.
* **`posterior`** — Posterior inference, which does a bottom-up traversal of the likelihood SPN.
* **`flatten`** — Flattening of the posterior SPN into mixture components.
* **`display/naming`** — Naming and annotation before output to console.
